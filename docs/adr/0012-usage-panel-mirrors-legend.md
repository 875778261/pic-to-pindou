# 用量面板：图例的第二个渲染器

屏幕上的用量面板与导出图纸的图例是同一份数据的两种渲染：条目、排序、色块、色号、颗数全部来自 `legendEntries()`（ADR-0008），面板只决定「怎么摆」。所以面板里没有独立的用量计算，也没有自己的排序规则。

两份渲染器的差别只在这三处：

- **容器**。图纸上是纸面宽度决定换行；屏幕上是右栏定高列表，色号多时在面板内滚动，页面高度不随色号数变化。
- **色块尺寸**。图纸上 14px 见方（印刷余量），屏幕上是 16px 见方（手指与视线的距离）。
- **数量上限**。图纸上一行能放几条由纸宽算；面板一列到底，不换行。

## 转换中不沿用旧条目

重算期间面板清空，只留一句「正在算用量…」。预览画布此时仍显示上一张图——两者不一致是有意的：画布的变化是连续的（拖住的那张图还在原地），数字却没有这层连续性，留着的旧颗数会被当成当前结果。转过半秒就回来，代价小于误读。

没有条目时的说明分两路：转换三态各有一句自己的文案；转不出图纸时直接用 store 的 `notice`（`describeRejection()` 已经把结构化原因讲成人话），界面不重写第二份。这也是 `state/notices.ts` 的原则——同一句话不在界面里各写一遍。

## 面板不承担布局

宽屏挂在右栏第三列，窄屏按单列顺序排在画布之后——这只是把面板摆到能放下的地方。断点、底部抽屉的用量档与贴边手势归 #9，面板本身不读写视口尺寸。

## 一个已知的小不一致

面板里的色块是屏幕色，与实物有偏差；这句提醒仍在左栏底部（`App.tsx`），不在面板内重复：它讲的是整张预览，而且面板只有 240px 宽，不值得为一句已经在场的话再占一行。

**Status**: accepted

**Considered Options**：
- 面板自己算一遍用量（否决——同一份数字两处算，改一处必漏一处，正是导出图例已经踩过的坑）
- 转换中保留旧条目加转圈遮罩（否决——遮罩挡不住数字，看起来仍是当前结果）
- 列表不限高、让页面跟着变长（否决——33 个色号就把右栏推到视口外，画布与用量对不上位置）
- 面板加色名（否决——MARD 无官方色名，ADR-0009）
- 面板自己判断点、自己开抽屉（否决——布局归 #9，两处判同一件事迟早不一致）

**Consequences**：
- 改图例条目的内容或排序只有一处可改；面板与图纸同时跟着变。
- 面板没有自己的用量状态：`pattern`、`status`、`notice` 都由 store 提供，条目在渲染期由 `legendEntries()` 推出。`useMemo` 只是跳过同一张图纸下的重复计算，不是一份可以过期的缓存。
- 手改单格（#8）落地后，面板随新 `pattern.counts` 更新——前提是手改走「换一个新 pattern」而不是就地改 `counts` 数组。
