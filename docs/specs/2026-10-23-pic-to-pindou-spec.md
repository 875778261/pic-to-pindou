## Problem Statement

我手上有张图片——一张照片、一张插画、一个游戏立绘——想把它摆成拼豆成品。但从"图片"到"能照着摆的图纸"中间隔着一堆手工活：

- 得先定网格多大，再反算成品尺寸和总颗数，算错就白摆。
- 得在有限的豆色里挑出能让结果看得出原图是什么的那几个颜色，凭肉眼对色必然出错，尤其是多种相近的棕和肤色。
- 得知道每个色号到底要买多少颗，否则下完单摆到一半发现少了。
- 网上现成的工具要么只把图变像素、不给色号，要么全英文、操作绕，手机上根本没法用。

结果就是：想做拼豆，卡在画图纸这一步上，还没开始摆就先累完了。

## Solution

浏览器打开就能用。把图片拖进来，定网格多大、限几个颜色，屏幕上立刻出现模拟成品的效果；不满意就拉滑块再调，看顺眼了导出 PNG 图纸——上面有网格、每格的色号、坐标和每个色号要买多少颗，照着摆就行。

图片不上传服务器，全程留在自己电脑上。电脑上用三栏布局，手机上画布满屏、参数收进底部抽屉，单指涂、双指缩放。

## User Stories

### 上传与输入

1. 作为一个拼豆玩家，我想把本地图片拖进页面就开始转换，这样不用先点开文件选择框再找。
2. 作为一个拼豆玩家，我想从手机相册直接选图，这样我在手机上也能用。
3. 作为一个拼豆玩家，我想知道支持哪些图片格式和多大体积，这样我不用拿一张十兆的图去试错。
4. 作为一个拼豆玩家，我想竖拍的照片横过来时方向是对的，这样我不用先手动旋转再上传。
5. 作为一个拼豆玩家，我想转换完再换一张图重来，这样我在试几张不同的图时不用刷新页面。
6. 作为一个拼豆玩家，我想确认我的图片不会被传到任何服务器，这样我敢上传有家人脸的照片。

### 网格尺寸与豆规格

7. 作为一个拼豆玩家，我想按"几块拼豆板"来定尺寸（1 块 29×29、4 块拼成 58×58 等），这样我手上有什么板就选什么。
8. 作为一个拼豆玩家，我想直接输入宽和高各多少颗，这样我不用被板的规格限死。
9. 作为一个拼豆玩家，我想看到锁定的宽高比，这样我知道原图的比例被保留还是被裁掉了。
10. 作为一个拼豆玩家，我想随时看到成品有多少厘米见方，这样我能判断做出来有多大、摆不摆得下。
11. 作为一个拼豆玩家，我想随时看到总颗数，这样我能估出要花多少时间。
12. 作为一个拼豆玩家，我想切换豆规格（2.6 / 5 / 10 毫米），这样同一张图纸我既知道用迷你豆多大、也知道用标准豆多大。
13. 作为一个拼豆玩家，我想在切换豆规格时画面本身不变，这样我知道变的只是成品尺寸而不是图纸内容。
14. 作为一个拼豆玩家，我想在超过 200×200 时被明确拦下来并被告知建议分图，这样我不会傻等一个注定跑不动的计算。

### 转换质量

15. 作为一个拼豆玩家，我想限制最多用几个色号，这样我一包一包买豆的时候不至于破产。
16. 作为一个拼豆玩家，我想看到实际用掉了几个色号，这样我能判断设的上限是不是太松。
17. 作为一个拼豆玩家，我想按需开抖动，这样我在追求更接近原图时有个选项。
18. 作为一个拼豆玩家，我想在抖动开关旁看到它的代价（会出现零散色点，可能要为一格开一包豆），这样我不会误以为那是 bug。
19. 作为一个拼豆玩家，我想调亮度、对比度、饱和度，这样一张发灰的照片也能出好结果。
20. 作为一个拼豆玩家，我想点一下图里的背景色把它设成"不摆豆"，这样白底照片不会长出一圈白豆。
21. 作为一个拼豆玩家，我想把多个颜色都设为空白，这样复杂的背景也能干净地去掉。
22. 作为一个拼豆玩家，我想在换参数后几百毫秒内看到结果，而且拖滑块时页面不卡，这样调参是顺畅的。

28. 作为一个拼豆玩家，我想看某格到底用了哪个色号，这样我能对着色卡确认。

### 手改

34. 作为一个拼豆玩家，我想在涂色时不会因为想平移画布而误涂一片，这样我不至于毁掉图纸。

35. 作为一个拼豆玩家，我想按颗数从多到少看到每个色号的用量，这样我先买用得最多的那几个。

## Implementation Decisions

**形态。** 单页纯静态应用，无路由、无后端、无账号。构建产物可直接静态托管。选 Vite + React + TypeScript，而非 Umi Max 或 Next.js —— 约定式路由、SSR、请求层在这里都无对应需求（ADR-0002）。

**风格。** Tailwind + 少量自建组件（滑块、色板网格、抽屉、色号列表）。不引 UI 组件库：本应用的核心 UI 是画布、色板、滑块，组件库最强的表格与表单能力用不上，却要付包体积与移动端适配的成本。

**状态。** 单一 zustand store。状态含源图、参数、网格、撤销栈、当前选中色号。用选择器订阅，避免"每色颗数"这类高频统计导致画布重渲染。

**色卡。** MARD 体系，分 221 标准档与 291 全系档（ADR-0005），不做跨品牌色号映射（ADR-0001 该条仍有效）。两档色号与屏幕色取自同一上游，保证换档不换色；色卡以类型化常量内置，LAB 值在模块初始化时预计算一次，不走异步请求。MARD 没有官方 RGB 发布，屏幕色只能证到"与所选上游一致"，界面须标注仅供参考。MARD 没有官方色名，色卡不设名称字段，以色号与系列标识。

**特种色。** 291 档里比 221 档多出的 70 个色号是珠光、夜光等特种色，照收进色卡并打标，但不参与量化选色（ADR-0006）；手改时仍可选用。

**网格编码。** 网格是唯一真源，手改直接写入同一份数据。编码：

```ts
// 0 = 空白格；i + 1 = 色卡第 i 项
type BeadGrid = { cols: number; rows: number; cells: Uint16Array }
```

不另建"手改覆盖层"：重算语义是覆盖手改（见下），覆盖层存在的唯一理由（钉住手改）因此不成立。撤销用网格快照，单步内存 80KB 量级，深度 50。

**图纸与色卡绑定。** 网格只存色卡下标，脱离档位就说不清指向哪个色号（291 档的图纸配 221 档色卡会越界），所以图纸是"色卡档位 + 网格 + 用到的色号 + 各色颗数"的整体，不把档位塞进网格结构里、也不让网格脱离档位单独流转。切换档位视同改参数：必须重算，有手改时先告知将丢弃多少处。

**豆规格不参与转换。** 豆规格只影响成品物理尺寸与颗数的换算常数。同一张图纸在三种规格下网格数据通用。

**色彩空间。** 色差用 CIEDE2000，不用 sRGB 欧氏距离 —— 后者在暗部与肤色区配错得肉眼可见，而人物与宠物照片是主要题材。

**采样。** 面积平均为主，源图尺寸接近目标网格整数倍时切最近邻（照片用最近邻会锯齿、像素画用面积平均会糊边）。判据自动计算，不交给用户。

**量化。** 在色卡内部选色，不采用"聚类后吸附最近色号"（ADR-0004）。先在候选色号里选出不超过 K 个（k-medoids，按各颜色像素数加权），再把每格映射到选中集合中最近的一个。候选集排除特种色（ADR-0006），291 档下实际为 221 个标准色。保证实际用色数 ≤ K，且每个用到的色号都真实存在。抖动默认关闭，作为可选的后处理。色差矩阵在 Worker 内惰性构建并缓存。

**Worker 边界。** 全部转换在 Web Worker 内完成，主线程只做绘制。消息带单调递增的 requestId，过期结果直接丢弃 —— 拉滑块会高频触发，不做队列，只认最后一次。

**渲染。** 按格宽切换画法：≥6px 用离屏单颗豆模板逐格绘制，<6px 把网格转成像素数据一次性输出（ADR-0003）。这不是两个独立功能，而是同一管线的两种输出形态；用户的风格切换只在大格宽时生效。两套画法共用同一坐标变换与视口裁剪。

**手势。** 双模式。查看态单指/拖动平移、双指/滚轮缩放；编辑态单指涂色、双指平移缩放。用显式按钮切换，因为不设模式会让"想挪画布"变成破坏性误涂。一次按下到抬起记为一步撤销。

**布局。** 断点切换：宽屏三栏，窄屏画布满屏 + 底部抽屉三档（参数 / 用量 / 图片）。

**图纸导出。** 离屏合成 PNG。含网格线、行列坐标、图例（色号 + 名称 + 颗数）、成品尺寸与总颗数。格数 ≤ 40 时每格标色号，超过则只标坐标 + 图例。空白格画成浅灰空心圆以区别于白色豆。

**明确不做编辑覆盖层、不做持久化。** 刷新页面即丢失，界面上要说明。

## Testing Decisions

**单接缝。** 整个转换管线暴露成一个纯函数作为唯一测试接缝：输入像素数据与参数，输出网格与用量统计。测试只打这里，不打内部步骤。UI、Canvas 绘制、手势都不写自动化测试。

**好测试的标准。** 只断言外部可观察行为：给定输入图片与参数，输出的网格与统计应当是什么。不断言中间过程、不断言内部函数调用次数、不对实现做白盒假设。凡是测了会"实现一改就得改测试"的，都不测。

**测什么。**

- 色差的正确性：用公开的标准测试对校验 CIEDE2000 实现。
- 采样的正确性：纯色图、棋盘图等构造输入下结果精确可预期。
- 量化的约束：任意 K 下，实际用色数 ≤ K，且每个用到的色号都在色卡里；限色保证不因聚类撞号而失效。
- 网格统计：颗数统计、总颗数、物理尺寸换算与手工算例一致。
- 空白格语义：被设为空白的颜色确认为编码 0，且不计入任何色号的颗数。
- 图纸排版判定：格数在 40 前后，是否标注格内色号的判定翻转正确。

**不测什么。** Canvas 实际像素（脆且价值低）、手势识别、组件渲染。坐标变换这类纯计算可以抽出来单独测。

**优先级。** 首次构建期，色差与量化两条是重点 —— 它们错了，整张图纸就是错的，而且错得不明显。

## Out of Scope

- 跨品牌色号映射（Perler / Hama 换号）。
- 账号、云端作品库、作品分享、链接分享。
- PDF 分板打印稿（每块板一页、带坐标）。
- 完整像素编辑器（画笔、油漆桶、选区、图层、对称绘制）。
- 自动抠图 / AI 前景分割。
- 抖动之外的高级抖动算法（有序抖动、蓝色噪声等）。
- 历史记录持久化、刷新恢复。
- 多语言、暗色主题（留待以后，不阻断当前设计）。

## Further Notes

**色号数据的可信度。** MARD 没有官方 RGB 发布，公开整理至少三份且互不相同，差异多在每通道 2–8。
屏幕色只能证到"与所选上游一致"，证不到"与实物一致"。色号本身仍可作下单依据。核对结论与量化差异见 `docs/reference/README.md`。

**仓库状态。** 仓库尚无任何提交。初始提交（含 AGENTS.md、术语表、四条 ADR、实施计划）由仓库所有者自行完成，自动化流程不执行任何 git 写操作。

**已确立的文档。** 领域词汇见术语表；六条决策记录：不做跨品牌映射、纯前端不上传、渲染按格宽切换、量化在色卡内选色、色卡改为 MARD 两档、特种色不进量化候选。

**后续可能重开的问题。** "重算覆盖手改"是当前选择。若实际使用中反复被抱怨，可考虑"钉住手改"的覆盖层方案 —— 但那会引入视觉不一致，需要重新设计而不是简单追加。
