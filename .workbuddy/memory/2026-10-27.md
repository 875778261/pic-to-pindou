## Cloudflare Workers 构建第二个坑：lockfile 只记了 Windows 平台

**现象**：`npm clean-install` 成功（added 59 packages），`npm run build` 里 `vite build` 报
`Error: Cannot find native binding` → `Cannot find module '@rolldown/binding-linux-x64-gnu'`（wasm 兜底也缺）。构建机 node 24.22.1 / npm 10.9.2。

**根因**：`package-lock.json` 是**增量 `npm install`** 产物，只写了当前平台的原生包 —— 66 条里只有
`@rolldown/binding-win32-x64-msvc`、`@esbuild/win32-x64`、`@tailwindcss/oxide-win32-x64-msvc`、`lightningcss-win32-x64-msvc`，
**linux 条目 0 条**。`npm ci` 严格照 lock 装，Linux 上 rolldown / oxide / lightningcss 全无原生模块。
同类风险面：任何跨平台 CI（GitHub Actions ubuntu-latest 也一样会挂）。

**验证过的修法**：删 lock 重新解析 → 66 → 119 条，linux 26 条。
- `npm install --package-lock-only` **修不了已有 lock**（照抄旧内容，`--os=linux --cpu=x64` 也无效），必须 `rm package-lock.json` 再装。
- 必须同时把 `@biomejs/biome` 钉成 `2.6.2`：重新解析会跳到 2.6.3，而 npmmirror 上 `@biomejs/cli-win32-x64@2.6.3` **404**，本机 lint 会挂。
- 重生成带来的其余差异（已接受）：`esbuild` / `@esbuild/win32-x64` 从树里消失（Vite 8 用 rolldown，实测不需要：无 esbuild 的树 177 测试 + build 全过）；`postcss` 8.5.31→8.5.32；`magic-string` 1.4.3→1.4.4（vitest 内嵌两处）。

**端到端验证**（`git archive develop` 纯净副本）：`npm ci` → `npm run build`（61 modules、265–338ms、产物与本地同尺寸）→ `npm run test` 177 全绿 → `npx biome check .` 干净（唯一报错是我脚本重写 package.json 时漏了行尾换行）。

**第三个坑（预先发现，未验证线上）**：Cloudflare 上建的是 **Workers 项目**（Deploy command `npx wrangler deploy`），仓库里没有 `wrangler.jsonc`。实测 `npx wrangler deploy --dry-run` 在无配置时报 `Missing entry-point`，要求补 `assets.directory: "./dist"`；补上后 dry-run 通过（`Read 6 files from .../dist`）。所以修 lock 之后还会在 deploy 阶段挂一次。

文档 `docs/plans/2026-10-26-deployment-plan.md` 已同步：A0 加「lockfile 平台覆盖检查」小节、方案 B 改成实际路径并补 wrangler.jsonc 说明、检查清单加两项。**未改仓库配置**（lock / package.json / wrangler.jsonc 都还没动），等 lhl 决定执行。

## 格内色号 + 预览贴顶：grill 定案（票 #11 / #12）

lhl 反馈「最终图纸上每粒豆没有色号，实际摆不知道自己用哪个颜色」，走 grill-with-docs 三轮定案。

**事实纠正（重要，别再说错）**：不是完全没标。导出图纸单边 ≤ 40 格才标格内色号（`LABELLED_CELL_LIMIT`），超过就只留行列坐标配图例；屏幕预览**从不标**。2 块板 29×58 这个最常用预设，第二维一过 40 就不标了 —— 阈值当年按「塞得下 4 个字符」估，而 MARD 色号实际只有 2–3 字符（291 色的 283 个色号里 3 字符 173、2 字符 110）。

**定案 A（ADR-0015，票 #11）**：判定依据从「格数」换成「格宽 + 字号」，分四级降级 —— 24px（字 ≈9）/ 21px（字 8，最后一档舒服的）/ 14–20px（字 6，硬下限 14）/ 4px 不标。判定收口到 `cellFitsCode(cellSize)` 单一函数；`labelled` 从输入变排版的**输出**；`LABELLED_CELL_LIMIT` 与 `labelsCellCodes()` 删除；坐标分档要另立 `COORDINATE_DENSE_LIMIT = 40`（原来借用色号阈值，概念串了）；`planExportLayout(input, limits)` 加注入口，否则「破上限」那条降级分支永远测不到；导出按钮不再预测标不标（拿不到排版算出的格宽与图例宽），改由导出后的消息带出。

**定案 B（ADR-0016，票 #12）**：预览纵向贴顶、横向仍居中。原 `placement()` 一条规则管两轴（小则居中），横图在竖直容器里纵向居中 → 上方一大片空白，看着像「图掉下去了」。贴顶的边距（避让浮在右上角的工具条）必须放 CSS，不能进 `placement()`：居中值在「装得下→装不下」临界点恰好是 0，加固定边距会让放大跨临界点时跳一个边距。

**中途作废的方案**：lhl 最初要「两处都标色号」，第二轮他自己推翻 → 预览不标。作废理由已进 ADR-0015 第 4 条（预览格宽随缩放变，同一张图会时标时不标，且满屏小字与「远观效果」的用途冲突）。

**分图（按 29×29 板切页）本轮不做**，另立项 —— 它是让 200×200 在纸上真可读的唯一办法，但会牵动「图例以整张图纸为 SSOT」（ADR-0008）。

**产物**：`docs/adr/0015`、`docs/adr/0016`、`docs/plans/2026-10-27-cell-code-and-top-align-plan.md`；`GLOSSARY.md` 改三条（格内色号 / 视口 / 预览）；ADR-0008 第 1 条与 ADR-0011 原点条款标注被取代。

**分辨率是下一件事（票 #13）**：每格只有 24×24 px、色号约 9px，1:1 打印只有 128–142 dpi。lhl 补充了真实要求：**导出的分辨率要随图纸大小变化**，不是所有网格都固定 24px/格 —— 固定格宽让成品越大 dpi 越低，大图纸反而最糊。票面因此从「加倍率」重写成「像素密度由成品物理尺寸 × 目标 dpi 推出」（`格宽 = dpi ÷ 25.4 × 豆规格mm`）。300dpi 下 29×29 / 58×58 做得到，**87×87 只能到约 198dpi、200×200 只有约 86dpi**（单边 8192 与面积 1670 万的硬事实）。
- 实现最容易翻车的点：**格宽搜索必须在代入目标密度之后判上限**，否则 87×87 会先判 24px 装得下、再乘成 59px 破面积上限，`toBlob` 返回 null；且所有几何（字号、页边距、图例尺寸、抬头行高）要一起乘。
- 待定三条写在票面：目标 dpi 怎么给、被上限压回时怎么办、**豆规格要不要参与密度换算**（参与的话同网格换规格导出像素会变，GLOSSARY 里「豆规格只是换算常数」那句话要改）。

**分图（按 29×29 板切页）lhl 明确暂缓**，理由与代价写在 #13 的「不做」段：会破图例 SSOT（ADR-0008/0012）、要重做坐标锚点与多文件下载，约 3–5 倍工作量。
